# 目标
设计“候选人能回答、岗位值得问、且本场尚未覆盖”的面试题。问题必须能追溯到简历/JD中的事实、能力或明确的技术主题。

## 适用场景
- 面试开始前规划主问题。
- 根据简历中的项目、实习经历设计深挖问题。
- 根据 JD 的能力要求补足八股、系统设计或工程权衡问题。
- 已有一批题目，需要避免语义重复但保留不同问题意图。

## 不适用场景
- 不负责给候选人回答打分；交给 `answer-evaluation`。
- 不负责判断是否应该继续追问；交给 `question-followup`。
- Eval 模式中不得访问真实面经作为 ground truth。

## 输入
至少需要：
- `resume_context`：候选人经历与技能事实。
- `jd_context`：岗位职责与要求。
- `covered_capabilities`：已经考察过的能力。
- `existing_questions`：本场已有题目。
- `target_count`：目标题数。

可选：题型配比、目标难度、题型限制、检索证据摘要。

## 步骤
1. 提取 JD 需要验证的能力，不把职位宣传语直接变成问题。
2. 从简历中选择可验证事实，优先选择候选人明确声称“做过”的内容。
3. 为每个考察点确定单一主意图，例如 `原因`、`方案`、`故障`、`权衡`。
4. 设计“事实锚点 + 技术任务 + 明确意图”的问题，避免纯知识点堆砌。
5. 检查问题是否要求候选人解释自己没有提供过的经历；发现则删除该假设。
6. 与已有题目做主题、事实锚点和 intent 三层去重。
7. 检查覆盖：项目深度、技术原理、边界条件、工程权衡、岗位相关性至少覆盖其中必要维度。

## 题目质量标准
一个合格主问题应当满足：
- 有明确对象：候选人的项目、技术机制或 JD 能力。
- 有明确动作：解释、设计、比较、定位、优化、分析等。
- 有单一主意图；可以有子问题，但不能同时考五六个互不相关主题。
- 能通过后续追问继续向深度推进。
- 与已问问题存在主题重合时，必须有明确不同 intent 或证据锚点。

## 项目题优先结构
`你在[项目事实]中做了X，请解释/设计/定位Y；重点说明Z约束或权衡。`

例如，不要只问“Redis缓存怎么做”，而应基于简历中的真实事实形成：“你在登录注册链路中将缓存查询下沉到 SDK Client，为什么先限流再查缓存？在缓存未命中时如何避免回源击穿？”

## 去重规则
按以下顺序判断：
1. 完全相同事实锚点 + 相同 intent：重复。
2. 高度相似事实锚点 + 相同 intent：重复。
3. 相同主题但 intent 不同：不自动判重。
4. 只有措辞不同而没有新的考察维度：仍视为重复。

## 输出
返回结构化题目：
```json
{
  "question": "...",
  "topic": "redis-cache",
  "intent": "tradeoff",
  "difficulty": "medium",
  "target_capabilities": ["高并发治理"],
  "evidence_source": "resume",
  "must_not_assume": ["未在简历中出现的技术"],
  "why_this_question": "..."
}
```

## 失败处理
- 找不到真实简历证据：退回到 JD 基础问题，并标注 `evidence_source=jd`。
- 已有题目全部重复：改变 intent 或考察维度，不仅仅改措辞。
- 候选人经历太薄：减少假设，采用事实确认型问题。
- Eval 模式需要面经：阻断该调用，要求使用 Golden Set 中的结构化证据。
