# 目标
让每一次追问都产生新的信息增量，而不是让模型把原问题换一种说法再问一次。

## 适用场景
- 主问题回答结束后的动态追问。
- 判断候选人是否只给结论、缺少实现原因或边界。
- 根据回答暴露出的知识空洞选择下一层问题。

## 核心递进链
优先使用：
`事实/现象 → 原理/原因 → 实现机制 → 边界/异常 → 权衡/替代方案`

不是所有问题都必须走满五层；当候选人已经给出充分证据时应停止追问。

## 是否追问
满足以下任一项时倾向追问：
- 回答只有结论，没有依据。
- 回答描述“做了什么”，没有说明“为什么这样做”。
- 回答缺少关键异常或边界处理。
- 候选人提出一个有价值但未解释的技术选择。
- 回答与简历事实存在潜在矛盾，需要澄清。

满足以下情况时停止：
- 已经覆盖目标 rubric。
- 继续问只会重复同一信息。
- 候选人已经进入与目标能力无关的细节。
- 达到 workflow 规定的最大追问次数。

## 追问步骤
1. 提取当前回答中的“已知信息”。
2. 找出缺失的信息维度：正确性、因果、实现、边界、权衡、验证。
3. 选择一个缺口，不一次问多个无关缺口。
4. 追问应引用候选人的上一句话，而不是重新描述原题。
5. 检查与上一轮追问是否重复。
6. 如果回答质量已经达到目标，返回 `need_followup=false`。

## 质量门槛
低质量追问通常有：
- “能再详细说说吗？”
- “为什么？”但没有对象。
- 把原问题完整复述一遍。
- 一次塞入四五个独立问题。
- 在没有证据时暗示候选人应该给出某个标准答案。

## 输出
```json
{
  "need_followup": true,
  "reason_code": "missing_boundary",
  "target_dimension": "boundary",
  "question": "如果 Redis 不可用，这个方案会退化到哪里？为什么这样设计？",
  "expected_new_information": ["降级策略", "依赖边界"]
}
```

## 失败处理
- 候选人说“不知道”：不要机械继续追问；记录知识缺口，可转到 review。
- 回答明显答非所问：先用一次澄清型追问重新锚定主题。
- 已达最大次数：必须停止，不因模型仍想追问而突破 Harness 限制。
