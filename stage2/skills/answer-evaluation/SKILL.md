# 目标
评价“答案本身”，而不是评价候选人的人格或潜力。评分必须基于问题要求与回答证据。

## 适用场景
- 主问题回答评分。
- 追问回答评分。
- 依据 rubric 识别回答深度、推理和边界缺口。

## 五维评价框架
1. `correctness`：技术事实、结论和概念是否正确。
2. `depth`：是否解释机制、原因、内部过程，而不是只给一句结论。
3. `reasoning`：是否存在完整因果链、取舍和分析过程。
4. `engineering`：是否考虑容量、异常、监控、部署、成本、可维护性等工程因素。
5. `boundary`：是否覆盖失败场景、约束、边界和替代方案。

## 评分原则
- 先提取问题要求，再读回答；不要先根据“说得像不像”打分。
- 每个维度只引用回答中的实际证据。
- 不因候选人没说题目未要求的知识而扣分。
- 不把语言流畅度当成技术正确性。
- “不知道”可以作为真实结果，但应记录为知识缺口，而不是虚构错误知识。

## 分数含义
- 5：目标维度完整、准确，并有关键实现或边界证据。
- 4：核心正确且基本完整，有少量深度缺口。
- 3：主要结论正确，但缺乏实现、因果或边界细节。
- 2：部分方向正确，但存在明显缺口或关键错误。
- 1：回答与问题基本无关、严重错误或只有空泛表述。

## 主问题与追问必须分开
主问题评分和追问评分分别存储：
```json
{
  "main_score": {...},
  "followup_scores": [{...}, {...}]
}
```
追问得分不能覆盖主问题得分；整场平均分的聚合规则必须由外部 Evaluation 层定义。

## 输出
```json
{
  "total": 3.8,
  "dimensions": {
    "correctness": 4,
    "depth": 3,
    "reasoning": 3,
    "engineering": 4,
    "boundary": 2
  },
  "evidence": ["..."],
  "strengths": ["..."],
  "gaps": ["..."],
  "next_focus": ["..."],
  "reason_code": "correct_but_shallow"
}
```

## 失败处理
- 问题本身有错误：先返回 `invalid_question`，不要把题目错误归咎于候选人。
- 无法确定事实：降低置信度并标注待核验，不编造标准答案。
- 回答为空：评分最低档，同时保留“无作答”状态。
